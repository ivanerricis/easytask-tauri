# Releasing EasyTask

Maintainer guide. Releases are built by `.github/workflows/release.yml` and always end as a **draft** GitHub Release:
nothing reaches users until you click "Publish".

## 1. One-time prerequisites

The in-app updater only installs updates signed with your key.

1. Generate the key pair: `npm run tauri signer generate -- -w ~/.tauri/easytask.key` (it asks for a password).
2. Put the **public** key in `src-tauri/tauri.conf.json` (`plugins.updater.pubkey`). Commit it. This is already done: the repository carries the real public key, so repeat this step only if you generate a new key pair.
3. Add two GitHub repository secrets (Settings > Secrets and variables > Actions):
   - `TAURI_SIGNING_PRIVATE_KEY`: the content of the private key file
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: its password

Keep the private key and its password in a password manager plus an offline backup. Never commit them.

**If the private key is lost**, installed apps can no longer verify new updates and will never update again.
Users must download and install a new build manually; that build must contain a new public key (generate a new pair, update `pubkey`, update the secrets).

## 2. Release steps

1. Make sure `master` is green on CI and contains everything you want to ship. Then start a release branch from it: `git switch master && git pull`, `git switch -c chore/release-X.Y.Z`.
2. Update `CHANGELOG.md` (Keep a Changelog format): rename the `## [Unreleased]` section to `## [X.Y.Z] - YYYY-MM-DD`, add a fresh empty `## [Unreleased]` above it and update the comparison links at the bottom. Do the same in `CHANGELOG.it.md`, with the Italian translation of the same section: the app shows the release notes in the language the user chose, and `npm run release:check` (and so the CI) fails when either file has no section for the version. The release pipeline puts both sections in the release notes, under `## English` and `## Italiano` (if `CHANGELOG.md` has none it falls back to the notes generated by GitHub).
3. Bump the version everywhere: `npm run release:bump X.Y.Z`
   (updates `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`; it does not commit, tag or push).
   `npm run release:check` verifies that the version files agree (CI runs it too).
4. Run the local checks (the VS Code task "Check: all (like CI)"): `npm run release:check`, `npx eslint .`, `npx tsc -b`, `npm run e2e:typecheck`, `npm run test`, `npm run build`, then in `src-tauri` `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`. `cargo fmt` and `e2e:typecheck` are not run by the Release workflow: only here (and in CI).
5. Commit and open a pull request: `git commit -am "chore(release): vX.Y.Z"`, `git push -u origin chore/release-X.Y.Z`, then a PR to `master` titled `chore(release): vX.Y.Z`. Merge it once CI is green.
6. Tag the merged `master` and push the tag: `git switch master && git pull`, then `powershell -NoProfile -ExecutionPolicy Bypass -File .vscode/release-preflight.ps1 -Version X.Y.Z` (if you have it: it checks branch, clean tree, version, changelogs and tag), `git tag vX.Y.Z`, `git push origin vX.Y.Z`.
   Pushing the tag should start the pipeline. If no Release run shows up (`gh run list --workflow release.yml -L 3`; it happened with 0.10.1), start it on the tag: `gh workflow run release.yml --ref vX.Y.Z`.
7. The pipeline runs three kinds of jobs; the last two run at the same time:
   1. **prepare** (Linux, seconds): fails fast unless the ref is a `v*` tag, checks that the versions and the tag agree, and extracts the release notes from `CHANGELOG.md` and `CHANGELOG.it.md` (it fails when the Italian section is missing). A failure here stops everything.
   2. **release** (Windows and Linux in parallel, right after `prepare`): builds the installers (NSIS on Windows; deb and AppImage on Linux), signs the updater artifacts (`.sig` files), and uploads everything, plus a merged `latest.json`, to a **draft** release named `EasyTask vX.Y.Z`. The Windows job also creates `EasyTask_X.Y.Z_x64_portable.zip` (`EasyTask.exe`, `portable.txt`, `LEGGIMI.txt`) from the executable it just built and uploads it to the same draft.
   3. **verify** (Linux, next to `release`): ESLint, `tsc`, unit tests, build, `cargo clippy`, `cargo test`. It does not hold the builds back, so **a red run means the draft must not be published**: fix it with a new PR and redo the tag. Always check that the whole run is green before publishing.
8. Open the draft in GitHub (Releases) and check the assets (see the list in section 5): installers, `.sig` files, `latest.json`, the portable zip.
   Optionally download and try the installer and the portable zip.
9. Check the release notes taken from the changelogs and edit them in the draft if needed. Keep the two `## English` / `## Italiano` headings: users see the section in their language in the "What's new" part of the update dialog and in Settings > About (the GitHub page shows both).
10. Click **Publish release**. Only then do users see it and does the updater consider it: the endpoint is `releases/latest/download/latest.json`, which resolves to the latest *published* release.

## 3. Not publishing by mistake, and undoing

- Ordinary commits and pushes release nothing. Only a pushed tag matching `v*`, or a manual run of the Release workflow on such a tag, starts it.
- Even then the result is a draft, invisible to users until published.
- **Delete a draft:** GitHub > Releases > open the draft > Delete.
- **Delete a wrong tag:** `git tag -d vX.Y.Z` and `git push origin :refs/tags/vX.Y.Z`. Delete the draft too, then fix, bump again if needed, and re-tag.
- If a release was already published with a problem, unpublish it (set it back to draft or delete it) so the updater stops offering it, then ship a new version; do not reuse a version number that users may already have installed.

## 4. What users see

- **Installed app (Windows):** a toast a few seconds after startup ("Update available") with an "Open About" action, and Settings > About, which also has a manual check. "Download and install" downloads, installs (passive mode) and restarts the app. The startup check can be turned off.
- **Portable app (Windows):** the same notice, but instead of installing it shows a hint and a link to the Releases page; the user replaces `EasyTask.exe` with the one from the new zip (the `data` folder is kept).
- **Linux:** the app uses the same updater endpoint, so Linux installs of the AppImage can use it; with the `.deb` and for any case where the in-app install is not wanted, download the new file from the Releases page. (Not tested on every distribution.)

## 5. Artifact names

- Installers use the `productName` and the version from `tauri.conf.json` (NSIS: `EasyTask_X.Y.Z_x64-setup.exe`; Linux: `.deb` and `.AppImage`), with matching `.sig` signature files, plus `latest.json`. Exact file names are chosen by Tauri's bundler: check them in the draft.
- The Cargo binary is named `EasyTask` (`[[bin]]` in `src-tauri/Cargo.toml`, same as `productName`), so it is `EasyTask.exe` (Windows) in `src-tauri/target/release`, in the installers and in the portable zip. The crate/package itself is still called `app`.
- Portable zip: `EasyTask_<package.json version>_x64_portable.zip`, containing `EasyTask.exe`, `portable.txt` and `LEGGIMI.txt` directly (no wrapping folder).
- `portable.txt` and `LEGGIMI.txt` come from `.github/portable/`.

## 6. Known limits and ideas

- **Windows code signing (future step):** binaries are not signed yet, so SmartScreen warns users. When it is added, the signing step goes in the `release` job of `release.yml` (before the artifacts are uploaded, so the updater signatures are computed on the signed files). Free options to look at for open source projects: SignPath Foundation. This is separate from the updater key above, which only protects updates.
- **Package managers:** winget and Scoop manifests could point at the published release assets.
- **macOS:** not built or tested. Adding it needs a macOS runner in the release matrix, the `dmg`/`app` bundle targets and Apple signing/notarization.
- **Manual runs (`workflow_dispatch`):** the workflow only works on version tags: started from a branch, the `verify` job fails immediately and nothing is built. To re-run a release by hand, pick the existing tag `vX.Y.Z` in the "Use workflow from" selector, so the run behaves like a tag push. Runs for the same ref are serialized (`concurrency`).
- **Pinned actions:** every GitHub Action is pinned to a full commit SHA (the version is in the trailing comment); Dependabot (`github-actions` ecosystem) opens the update pull requests.
- The e2e job in CI is not part of the release pipeline. On Windows it runs only by hand (`workflow_dispatch`): on the hosted runner the elevated user keeps WebView2 from opening its debug port.
- **Security checks:** CI runs `cargo audit`, `cargo deny check` (config in `src-tauri/deny.toml`) and `npm audit`. `deny.toml` accepts the yanked `zip` 4.6.1 pulled in by `tauri-plugin-updater`: remove the exception once the plugin moves to a newer `zip`.

## 7. Checklist

```
[ ] One time: updater key generated, pubkey in tauri.conf.json, both secrets set
[ ] master is green on CI
[ ] Branch chore/release-X.Y.Z from master
[ ] CHANGELOG.md and CHANGELOG.it.md: [Unreleased] renamed to [X.Y.Z] with the date
[ ] npm run release:bump X.Y.Z
[ ] npm run release:check passes, local checks pass
[ ] git commit -am "chore(release): vX.Y.Z", push, PR to master
[ ] PR green on CI and merged
[ ] On the updated master: git tag vX.Y.Z, git push origin vX.Y.Z
[ ] Release workflow started (else: gh workflow run release.yml --ref vX.Y.Z)
[ ] Release workflow green (verify, release x2, portable)
[ ] Draft contains: NSIS installer, deb, AppImage, .sig files, latest.json, portable zip
[ ] Installer and portable zip tried (optional but recommended)
[ ] Release notes (English and Italian, from the changelogs) checked
[ ] Publish release
[ ] Check "Check for updates" from the previous version
```
